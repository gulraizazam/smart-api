1. Overview & Objectives
Complete, consolidated build specification for the Cash Flow & Expense Management module within the Cutera CRM. Supersedes all previous documents.

1.1 Primary Objectives
Real-time cash position: Exact balance at every branch, head office, and bank at any moment.
Expense tracking: Every outgoing payment documented with source, beneficiary, receipts, and vendor/staff linkage.
Vendor accountability: Ledgers for everyone the business pays — suppliers, landlords, lawyers, service providers.
Team accountability: Track cash advances and expense submissions per staff member.
Fraud prevention: Built-in controls against financial manipulation by any party.
Access control: Granular role-based permissions. Least privilege.
Audit safety: Immutable action log. No record ever truly deleted.

1.2 What This Module Does NOT Do
NOT a full accounting/ERP system.
NOT an invoicing system (patient invoices handled elsewhere).
NOT payroll (salaries recorded as expenses, not computed).

2. System Context & Assumptions
2.1 Operational Reality
Cash stays at branches: Each branch collects and holds cash.
Head office as cash hub: Receives surplus cash from branches. Makes expenses directly.
Cross-branch payments: Expense for Branch A can be paid from Branch B, HO, or bank.
Centralized accounting: One accountant (expandable). Entry creation for small amounts = approval. Large amounts need admin approval.
Single bank account: One bank for business. Schema supports more.
Dynamic branches: Currently 12. System reads dynamically.
Patient refunds: Handled by existing CRM. Refunds reduce pool balance through existing payment data. No action needed in this module.

3. Module Initialization (Go-Live)
One-time setup when module is first deployed. Admin only.

3.1 Go-Live Date
Admin sets go-live date in Settings (e.g., April 1, 2026).
All patient payment queries filter by: payment_date >= go_live_date.
Historical payments before this date NOT included — value captured in opening balances.
Go-live date frozen after first period lock.
⚠ SECURITY: Without this filter, cash flow includes years of historical payments without matching expenses. All numbers wrong.

During the first month before the first period lock, admin can reset the entire module — wipe all data and start fresh. This is a safety net in case setup was done incorrectly.

4.2 Auto-Creation & Deactivation
Laravel Observer on Branch model detects new active branch → creates pool → notifies admin.
Branch deactivated → pool soft-deactivated → hidden from dropdowns → stays in reports.
Branch deactivated with balance > 0 → system prompts admin to transfer remaining balance to HO before deactivation completes.

Cash at branch → that branch’s cash pool
Credit Card → bank account pool (settlement timing not tracked)
Bank Transfer → bank account pool
Configurable in Settings.

Balance = Opening + Inflows – Outflows + Transfers In – Transfers Out
ℹ IMPL: cached_balance via Observer. Dashboard reads cache; reports use true calculation.

5.2 Expense Approval Flow
Below PKR 10,000 Threshold
Accountant saves → status = 'approved' (auto) → pool balance affected → done.
Above PKR 10,000 Threshold
Accountant saves → status = 'pending' → pool balance affected immediately (cash already spent).
Admin receives in-app notification. Sees entry in Pending Actions widget on dashboard.
Admin reviews: sees amount, description, category, pool, attachment preview.
Attachment MUST be present before admin can click Approve (for above-threshold expenses).
Admin approves → status = 'approved', badge removed. Done.
Admin rejects → status = 'rejected', rejection reason mandatory, pool balance REVERSED, accountant notified.
Accountant edits rejected entry and resubmits → status back to 'pending', pool balance affected again.
⚠ SECURITY: This is the ONLY case where accountant can edit an entry — resubmitting a rejected expense.

8. Team/Staff Expense Ledger
Tracks cash advances and expense accountability.
⚠ SECURITY: Only users marked as 'eligible for advances' by admin can receive advances. Not all CRM users.

8.1 Flow
Accountant gives eligible staff cash from pool (Advance). No approval needed.
Staff makes purchases, gets receipts.
Accountant records expense with staff in 'Expense By' (reduces advance balance).
Leftover returned to any active pool (Return). Balance should reach zero.

8.2 Balance
Balance = Advances – Expenses – Returns
Positive = unaccounted cash. Dashboard highlights.

8.3 Rules
Advance from one pool, return to any active pool (can differ).
Warn (not block) if staff already has unsettled advance.
Return cannot exceed balance.
System flags perfect-match advances (expenses = advance, zero return).

10A. Real-World Workflow Examples
These examples document how common business scenarios are recorded in the system. They serve as reference for the developer and for training.

10A.1 Meta Ads Payment
Business collects cash from multiple branches to pay Meta for Facebook ads.
Step 1: Record cash transfers from each contributing branch to Head Office (physical_cash method).
Step 2: Record expense: Category = Marketing, Vendor = Meta, Paid From = Head Office Cash (or whichever pool the cash was consolidated into), For Branch = General / Company-wide, Payment Method = Cash, Attachment = deposit slip to Meta’s bank.

10A.2 Monthly Salaries
One bulk expense entry for all staff salaries combined.
Category = Salaries & Wages, Paid From = Bank Account (salaries paid via bank), For Branch = General / Company-wide, Amount = total salary bill.
Doctors are salaried — included in same entry or separate entry under same Salaries category.

10A.3 Utility Bills
Each branch’s utility bill is a separate expense entry.
Lahore DHA electricity: Category = Utilities, Paid From = depends on who pays, For Branch = Lahore DHA, Vendor = LESCO (the utility company).
12 branches = 12 separate entries for electricity. Same for gas, water, internet if applicable.

10A.4 Branch Rent
Head Office pays all branch rents centrally.
Category = Rent & Property, Paid From = Head Office Cash or Bank Account, For Branch = the specific branch (e.g., Islamabad), Vendor = landlord.

10A.5 Accountant on Leave
Accountant is absent for a few days. Branches still spend cash.
Entries wait until accountant returns. They will be backdated (expense date = actual date, not entry date).
Backdated entry flag will trigger (if > 7 days old). This is expected in this scenario — admin will see the flags and understand why.
No one else can enter expenses. This is by design — keeps accountability with one person.

10A.6 Emergency Branch Expense
Branch manager pays electrician 5k cash for urgent AC repair. Accountant is remote.
Branch manager informs accountant via call/WhatsApp.
Accountant records: Category = Equipment & Machinery, Paid From = that branch’s cash pool, For Branch = that branch, Payment Method = Cash, Attachment = photo of receipt sent by branch.

10A.7 Branch Closure
Rare scenario: a branch is permanently closed.
Branch deactivated in CRM.
Cash pool auto-deactivated. If balance > 0, system prompts admin to transfer remaining cash to Head Office.
Pool hidden from dropdowns. All historical data preserved in reports.

10A.8 Card Processing Fees
Bank deducts card processing fees from card settlements.
Record as a separate expense: Category = Bank Charges, Paid From = Bank Account, For Branch = General / Company-wide, Payment Method = Bank Transfer. No cash attachment needed.

19.1 Expenses
Amount > 0 (integer). Date not future. Not in locked period. Pool active.
Below 10k: auto-approved. Above 10k: pending admin approval.
Cash payment: attachment mandatory.
Accountant edits ONLY rejected entries. Admin edits any (reason mandatory).
Void: admin only, reason mandatory, reversal entry.
Vendor selected → auto vendor payment. Staff selected → auto reduce advance.
Rejected: balance reversed. Resubmitted: balance re-applied.

19.2 Transfers
From ≠ To. Amount > 0. Date not future/locked. Reference + attachment always required.
No approval. Warn if negative. Two methods only: physical_cash, bank_deposit.

19.3 Vendors
Admin-only CRUD. Accountant suggests. Name unique (case-insensitive). No hard delete.

19.4 Staff
Only advance-eligible users. Warn existing balance > 0. Return cannot exceed balance.
Advance from any pool, return to any pool.

19.5 Reconciliation
Sum(Pool Balances) = Patient Payments – Expenses + Opening Balances – Staff Advances
Manual button on dashboard. Admin clicks → green/red result.

25. Operational Context (How The Business Works)
This section documents the real-world operational context that drives design decisions. The developer must understand this context to build the right system.

25.1 Daily Operations
10–20 expense entries per day across all 12+ branches and HO.
Accountant enters expenses throughout the day as they happen — not in batch at end of day.
Branches communicate expenses to accountant via phone calls and WhatsApp messages. Receipts are often photos sent via WhatsApp, then uploaded to Google Drive.
There is currently 1 accountant. System designed to support multiple accountants in future (same role, same permissions). 1 admin.
If accountant is on leave, entries wait until they return. Entries are backdated (expense date = actual date). Backdated flag will trigger — this is expected behavior. No one else enters expenses.

25.2 Cash Movement
Cash stays at branches. Each branch physically holds its cash. Expenses typically paid from branch cash.
Head Office also holds cash and makes expenses directly.
Cash transfers: a trusted staff member physically carries cash from branch to HO. No armored transport, no digital transfer of cash.
There is NO confirmation from the receiving end. Accountant records the transfer and that is sufficient. The FDM screen serves as a secondary check — FDM can see the outflow and verify the amount left.
HO or branches deposit cash at the bank physically. Someone goes to the bank with cash.
No bank withdrawals are made. Money flows: branches → HO and/or bank. Never bank → branch.

25.3 Payment Patterns
Salaries: one bulk entry for all staff combined. Not per employee. Doctors are salaried employees, not consultants. Included in Salaries category.
Utility bills: one entry per bill per branch. 12 branches = 12 electricity entries.
Rent: Head Office pays all branch rents centrally. Paid From = HO Cash or Bank, For Branch = specific branch.
Meta/Google ads: cash collected from multiple branches via transfers, consolidated, then paid as one Marketing expense. For Branch = General / Company-wide.
Card processing fees: bank auto-deducts. Recorded as separate Bank Charges expense.
Credit card patient payments: mapped to bank pool immediately. Settlement timing (1–3 day delay) not tracked.
Patient refunds: handled by existing CRM payment system. Refunds reduce pool balance through existing data. No action in this module.

25.4 Admin Workflow
Admin checks dashboard daily for: pending approvals, flagged entries, pool balances.
Admin runs reports monthly for deeper analysis.
Branch managers only see dashboard (their branch). No report access. No data entry.
FDMs see only their branch cash view. No disputes in system — handled offline.

25.5 Branch Lifecycle
Currently 12 branches. System reads dynamically — never hardcode branch count.
New branch: pool auto-created with balance 0. Admin notified to set opening balance.
Branch closure (rare but happened once): pool soft-deactivated. If balance > 0, admin prompted to transfer remaining cash to HO. Pool hidden from dropdowns. All historical data preserved.

26. Design Decisions & Rationale
Every major design choice was discussed and decided by the product owner. This section documents the reasoning so the developer does not accidentally reverse or question these decisions.

26.1 No Smart Defaults (Except Date)
Decision: Only Expense Date pre-fills with today. All other fields (Paid From, For Branch, Category, Payment Method, Vendor, Staff, Description, Reference) start empty every time. After save, form resets completely.
Rationale: If fields pre-fill with last-used values or smart suggestions, the accountant can submit the form without actively reviewing every field. This leads to wrong records — expenses tagged to the wrong branch, wrong pool, or wrong vendor. Since 10–20 entries happen daily, even a small error rate compounds.
⚠ SECURITY: Do NOT add session memory, last-used values, or auto-populate logic. This was explicitly rejected.

26.2 Cash Attachment Mandatory, Card/Bank Optional
Decision: Cash expenses MUST have a Google Drive attachment. Credit card and bank transfer expenses do not require attachment.
Rationale: The bank account has its own controls — cheque signatories, online banking approvals, statement records. Nobody can steal from the bank without external checks. But cash is physically held at branches and HO. Without receipts, it’s easy to record a fake cash expense and pocket the money. Mandatory cash receipts make this much harder.

26.3 No Automated Reconciliation
Decision: No nightly reconciliation job. Instead, a manual 'Run Reconciliation Check' button on the dashboard.
Rationale: Admin prefers manual control over automated background processes. When admin wants to verify, they click the button and get an immediate green/red result. No daily_reconciliation_snapshots table needed.

26.4 Accountant Cannot Edit
Decision: Accountant can create entries but cannot edit them. Only admin can edit (with mandatory reason). The sole exception: accountant can edit a rejected entry to fix and resubmit it.
Rationale: Prevents post-hoc manipulation. If the accountant could edit, they could create an entry, wait for it to pass review, then quietly change the amount or vendor. By restricting edits to admin only (with a mandatory reason logged in audit trail), every change has accountability.

26.5 Transfers Don’t Need Approval
Decision: Cash transfers go through immediately regardless of amount. No pending/approval flow.
Rationale: Transfers don’t create or destroy money — they just move it between pools. Total business cash stays the same. The real risk is in expenses (money leaving the business), not transfers. Reference and attachment are mandatory for every transfer, providing audit trail.

26.6 FDM Read-Only, No Dispute Button
Decision: FDM can only view their branch cash. No entry, no edit, no export, no dispute button.
Rationale: Disputes happen through offline conversation (phone/WhatsApp). Adding a dispute feature adds UI complexity without clear workflow resolution. The FDM screen’s value is visibility and deterrence, not interactive dispute management.

26.7 PKR 10,000 Approval Threshold (Not 50,000)
Decision: Expenses above PKR 10,000 need admin approval. Initial design was 50,000 but the product owner chose tighter control.
Rationale: In this business context, 10k is a meaningful amount. A 50k threshold would let too many mid-range expenses pass without review. The 10k threshold ensures admin sees all significant spending while still allowing small routine purchases to flow instantly.

26.8 Removed Features
Vendor Payment Nudge — Removed
Was: When expense > 10k without vendor, system prompts 'Is this a vendor payment?'
Why removed: Unnecessary friction. Many legitimate expenses above 10k have no vendor (salaries, utilities, government fees). The vendor field is always visible with category-based emphasis — that’s enough.

HO + General Over-Tagging Warning — Removed
Was: Alert if > 30% of expenses tagged as HO or General.
Why removed: Not useful for this business. HO genuinely pays many expenses centrally (all rents, salaries, marketing). A 30% threshold would always trigger false alarms.

26.9 Doctors Under Salaries
Decision: No separate 'Doctor Payments' category. Doctors are salaried employees. Their pay goes under 'Salaries & Wages'.
Rationale: In this business, doctors are not consultants paid per session. They are salaried staff. A separate category would be misleading and unused.

26.10 Whole Numbers Only
Decision: UI accepts and displays whole PKR amounts only. No decimal input, no paisa shown.
Rationale: Nobody deals in paisa in Pakistani business transactions. Database stores DECIMAL(15,2) for technical safety, but the UI layer enforces integer-only input and display.

26.11 Google Drive Only for Attachments
Decision: All attachments are Google Drive URLs. No file upload to CRM server.
Rationale: Business already uses Google Drive for document management. Receipts are typically photos taken on phone, sent via WhatsApp, then uploaded to Drive by the accountant. Drive provides its own access control, versioning, and storage. Uploading to the CRM server would require storage management, backup, and serving infrastructure that isn’t needed.

26.12 ‘For Branch’ Must Be Selected
Decision: 'For Branch' is mandatory. The option to leave it blank was explicitly rejected.
Rationale: If blank is allowed, lazy entries would have no branch tag and wouldn’t appear in any branch report. Every expense must be attributed: specific branch, Head Office, or General / Company-wide. These three options cover all scenarios.

26.13 No Live Dashboard Updates
Decision: Dashboard does not auto-refresh. User presses F5 or navigates back to refresh.
Rationale: With 10–20 entries/day, real-time updates add engineering complexity (WebSockets/polling) for minimal benefit. The admin checks the dashboard periodically, not watching it continuously.

27. Implementation Notes for Developer
Technical details and gotchas the developer must know.

27.1 Branch Filtering
Do NOT build a new branch access system. Reuse the existing CRM pattern.
Look at how other modules (appointments, patients) filter data by user’s assigned branches.
Use the exact same approach: scope/trait that reads the user’s branch assignment and filters queries.
Users table already has branch assignment (check: could be a pivot table or FK). The cash flow module just reads it.

27.2 Payment Methods
Do NOT create a new payment methods table or enum for this module.
Read from the existing CRM payment method configuration (same methods used for patient payments).
Currently: Cash, Credit Card, Bank Transfer. If new methods are added to CRM, they automatically appear in expense form.

27.3 Dropdowns
Do NOT introduce a new dropdown library or component.
Use the existing CRM searchable dropdown component (same one used for patient search).
All dropdowns: show full list on click + search/type-ahead box at top.
Apply to: Paid From, For Branch, Category, Payment Method, Vendor, Staff, Transfer pools.

27.4 Google Drive Attachment
Validate URL with regex: must match drive.google.com or docs.google.com patterns.
Custom Laravel validation rule: new GoogleDriveUrlRule.
Display on dashboard/approval: clickable link that opens in new tab.
Do NOT attempt iframe embedding — Google Drive does not reliably support it.
Non-matching URLs: show warning but do not block save (except for cash expenses where attachment is mandatory).

27.5 Advance-Eligible Users
Add a boolean column (e.g., is_advance_eligible) to the existing users table via migration.
Admin manages this in Settings screen.
Only users with this flag = true appear in the staff dropdown when giving advances.

27.6 Vendor & Category Requests
vendor_requests table: id, name, phone, note, requested_by (FK), status (pending|approved|dismissed), admin_notes, created_at/updated_at.

Unread count badge on bell icon.
Use Laravel’s built-in notification system if available in this CRM, or build a simple polling mechanism.

27.8 Scheduled Jobs
Daily digest: Laravel Mailable + Kernel.php schedule. Queued. Configurable send time from cashflow_settings.
Monthly report: scheduled for 1st of each month. Generates summary of previous month.
Both should fail gracefully and log errors, not crash.

27.9 Module Reset
Available only before first period lock. Check: period_locks table empty.
Implementation: truncate all cashflow_* tables (except cashflow_settings). Re-seed category defaults.
Requires double confirmation: 'Are you sure?' → 'Type RESET to confirm'.
Log the reset action in audit trail BEFORE truncating (write to a separate log or preserve audit entry).
After first period lock: hide the reset button entirely. Do not just disable — hide.

27.10 Cached Balance Updates
Use Laravel Observers on: Expense, CashTransfer, VendorTransaction, StaffAdvance, StaffReturn models.
On created/updated/deleted: recalculate the affected cash_pool.cached_balance and/or vendor.cached_balance.
Use DB::transaction for the recalculation to avoid race conditions.
Dashboard reads cached_balance. Reports use true SUM() calculation.
Reconciliation check button compares cached vs calculated and shows discrepancy.

27.11 Approval Balance Logic
This is the most complex balance flow. Pay careful attention:
Expense created below threshold → status = 'approved' → pool balance decremented.
Expense created above threshold → status = 'pending' → pool balance decremented immediately (cash is physically spent).
Admin approves → status = 'approved'. No balance change (already decremented).
Admin rejects → status = 'rejected' → pool balance INCREMENTED (reversal). Rejection reason saved. Accountant notified.
Accountant edits rejected entry → status back to 'pending' → pool balance decremented again.
Admin approves resubmission → status = 'approved'. No balance change.
Admin rejects again → balance reversed again. Cycle can repeat.
⚠ SECURITY: Every status transition must be wrapped in DB::transaction with the balance update. Test this thoroughly.
27.12 Existing CRM Integration (Critical First Step)
This module is NOT a standalone system. It is built inside the existing Cutera CRM codebase, using the same database, same authentication, same UI framework, same conventions.
Before writing any code, the developer MUST explore the existing codebase and map these integration points:
Branches table: Table name, structure, active/inactive flag, how branches are created/managed. The Branch Observer depends on this.
Users table: Structure, role/permission system (Spatie or custom?), how branch assignment works (FK, pivot table, JSON column?). Needed for branch filtering, advance eligibility, and role-based access.
Patient payments table: Table name, columns for amount, payment method, branch, date. This is the READ-ONLY inflow source. The go-live date filter applies here.
Payment methods: How they are stored and configured. This module reads from the same config — does not create its own.
Permission/role system: How existing roles and permissions are defined. New cash flow permissions must follow the same pattern.
Searchable dropdown component: Which component/library is used for patient search. All cash flow dropdowns must use this exact component.
UI framework: CSS framework, component library, layout patterns, sidebar navigation structure. The cash flow screens must look identical to existing screens.
Laravel version, auth guard, queue driver, mail driver: These affect how notifications, scheduled jobs, and emails are implemented.
Notification system: Does the CRM already have an in-app notification system (bell icon)? If yes, reuse it. If no, build one that can be reused by other modules.
Folder structure and naming conventions: Controllers, Models, Services, routes, views — follow whatever pattern already exists. Do not introduce new conventions.
The product owner will provide full codebase and database access. The developer should spend the first portion of Phase 1 exploring and documenting these integration points before writing any migration or model.
